# ChatGPT WhatsApp Bot

A Node.js application that integrates OpenAI's ChatGPT with WhatsApp through Twilio, allowing users to interact with AI directly through WhatsApp messages with subscription-based token management.

![Chat Example](chat-example.jpeg)

## Features

- 🤖 **AI-Powered Conversations**: Interact with OpenAI's GPT model through WhatsApp
- 📱 **WhatsApp Integration**: Seamless messaging through Twilio's WhatsApp API
- 💳 **Subscription Management**: Token-based usage with subscription tiers
- 🔒 **Secure Configuration**: Environment-based configuration for API keys
- 📊 **Session Tracking**: Track message counts per user session

## How It Works

### 1. Message Flow
1. User sends a WhatsApp message to your Twilio number
2. Twilio forwards the message to your webhook endpoint (`/sms`)
3. The bot checks the user's subscription status
4. Based on subscription status, the bot either:
   - Processes the message with ChatGPT
   - Prompts for subscription/token setup
   - Requests subscription upgrade

### 2. Subscription States

#### New User (No Subscription)
- User receives: "Please give me your required tokens"
- User sends a number to set their token limit
- System creates subscription with specified tokens

#### Inactive Subscription
- User receives: "You don't have an active subscription. Please visit our website to view our plans"

#### Active Subscription
- Message is sent to OpenAI's GPT model
- Response is generated using user's available tokens
- Reply is sent back through WhatsApp

### 3. Architecture

```
WhatsApp User → Twilio → Your Server → Subscription API
                    ↓
              OpenAI GPT API → Response → WhatsApp User
```

## Convex Setup

This project uses [Convex](https://convex.dev) as its database backend for storing users, identities, and messages.

### Data Model

| Table | Purpose |
|---|---|
| `users` | One row per unique person |
| `identities` | One row per `(channel, address)` pair, linked to a user |
| `messages` | One row per inbound/outbound message; deduplicated by `providerMsgId` |
| `reminders` | One row per reminder intent; status: queued → sent / failed / cancelled |
| `deliveries` | One row per delivery attempt; queried by the 1-minute cron |

### Delivery Scheduler

A Convex cron job (`convex/crons.js`) runs every **1 minute** and processes queued deliveries via `convex/deliveries.js → processQueue`.

`processQueue` runs as an **internalAction** (not a mutation) so it can make the Telegram `sendMessage` HTTP request. For each due queued delivery it:
1. Resolves the target chat ID from the delivery → reminder → identity chain.
2. POSTs to `https://api.telegram.org/bot{token}/sendMessage`.
3. On success: marks `delivery.status = "sent"` and `reminder.status = "sent"`.
4. On failure: marks `delivery.status = "failed"` with a `failureReason`; the rest of the batch continues.

### Env Vars

| Variable | Required for | Where it comes from |
|---|---|---|
| `CONVEX_URL` | All | Auto-generated by `npx convex dev` into `.env.local`; copy to `.env` |
| `TELEGRAM_BOT_TOKEN` | Telegram delivery | Must be set **inside Convex** (see below) |
| `TWILIO_ACCOUNT_SID` | WhatsApp delivery | Your Twilio Account SID — must be set **inside Convex** |
| `TWILIO_AUTH_TOKEN` | WhatsApp delivery | Your Twilio Auth Token — must be set **inside Convex** |
| `TWILIO_WHATSAPP_FROM` | WhatsApp delivery | Your Twilio WhatsApp sender number, e.g. `+15551234567` or `whatsapp:+15551234567` — must be set **inside Convex** |

> These variables must be registered **in Convex** (not just in `.env`) because the delivery cron runs inside Convex, not your Node server.

#### Setting Convex env vars

**Local dev** — run once after `npx convex dev` has authenticated:
```bash
npx convex env set TELEGRAM_BOT_TOKEN 123456789:ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghi
npx convex env set TWILIO_ACCOUNT_SID  ACxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
npx convex env set TWILIO_AUTH_TOKEN   your_auth_token_here
npx convex env set TWILIO_WHATSAPP_FROM +15551234567
```

**Production** — in the [Convex dashboard](https://dashboard.convex.dev), open your deployment → **Settings → Environment Variables** → add each variable above.

> If any Twilio variable is missing the cron marks only the affected WhatsApp deliveries as `"failed"` with a clear `failureReason`; Telegram deliveries and the rest of the batch are unaffected.

**First-time setup** (requires GitHub login in browser):
```bash

```
This authenticates your machine, creates a dev deployment, and starts watching `convex/` for changes. The `CONVEX_URL` value will be printed to the console and written to `.env.local`.

**Running both servers together:**
```bash

npm run convex:dev

# In another terminal — Node/Express server
npm run dev

# Or run both at once (requires the app to be bootstrapped first)
```

```js
const { ConvexHttpClient } = require("convex/browser");
const { api } = require("./convex/_generated/api_cjs.cjs");

const client = new ConvexHttpClient(process.env.CONVEX_URL);

await client.mutation(api.messages.upsertIdentityAndLogMessage, {

  providerMsgId: req.body.MessageSid,
  direction:     "inbound",
  text:          req.body.Body,
  rawPayload:    JSON.stringify(req.body),
});
```

## Outlook Calendar OAuth Setup

The server exposes two routes for linking a user's Microsoft account:

| Route | Purpose |
|---|---|
| `GET /connect/outlook?identityId=<id>` | Redirects the user to the Microsoft consent screen |
| `GET /auth/outlook/callback` | Receives the authorization code, exchanges it for tokens, persists account + tokens in Convex |

After a successful callback the user sees a confirmation page. No calendar events are created yet — this task only wires up the auth flow.

### Azure App Registration

1. Go to [portal.azure.com](https://portal.azure.com) → **App registrations** → **New registration**.
2. Set a redirect URI: `https://yourdomain.com/auth/outlook/callback` (Web platform).
3. Under **API permissions** add delegated permissions: `User.Read`, `Calendars.ReadWrite`, `offline_access`.
4. Under **Certificates & secrets** create a new client secret.
5. Copy the **Application (client) ID** and the **client secret value**.

### Env Vars (Node server — `.env`)

| Variable | Description |
|---|---|
| `MS_CLIENT_ID` | Azure Application (client) ID |
| `MS_CLIENT_SECRET` | Azure client secret value |
| `MS_TENANT` | `common` for multi-tenant, or your directory tenant ID |
| `MS_REDIRECT_URI` | Must exactly match the redirect URI registered in Azure |

### Env Vars (Convex — for token refresh action)

The `refreshMicrosoftToken` action runs inside Convex and needs the client credentials:

```bash
npx convex env set MS_CLIENT_ID     your_client_id
npx convex env set MS_CLIENT_SECRET your_client_secret
npx convex env set MS_TENANT        common
```

### Initiating the flow

Obtain the user's `identityId` from the `identities` table in Convex (it is returned by `upsertIdentityAndLogMessage` after the user's first message), then direct the user to:

```
https://yourdomain.com/connect/outlook?identityId=<convex_identity_id>
```

### Schema field mapping

Google credentials are stored in the existing `oauth_accounts` and `oauth_tokens` tables with `provider = "google"`:

## Telegram Bot Setup

The bot exposes `POST /telegram/webhook` to receive inbound Telegram messages and reply with `"Saved."`.

### Telegram Commands

| Command | Example | Effect |
|---|---|---|
| `remind …` / `/remind …` | `Remind me to call John on Friday at 9am` | Extracts reminder via OpenAI, stores in Convex, schedules delivery, creates Outlook event if account linked |
| `cancel <id>` / `/cancel <id>` | `/cancel k17abc123def456` | Cancels the reminder and its queued delivery; queues a calendar delete job for every connected calendar (Microsoft, Google) that has a stored event ID — repeated calls are safe and will re-trigger a delete if a prior attempt failed |

**Getting a reminder ID**: the ID is shown in the bot's confirmation reply when a reminder is created:
```
✅ Reminder set: "Call John" at 2026-03-13T09:00:00 (Australia/Adelaide)
ID: k17abc123def456

To cancel: /cancel k17abc123def456
```

### Prerequisites
- A Telegram bot token from [@BotFather](https://t.me/BotFather) (`/newbot` → copy the token)
- A publicly accessible HTTPS URL for your server (use [ngrok](https://ngrok.com) for local dev)

### Env var
```env
TELEGRAM_BOT_TOKEN=123456789:ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghi
```

If `TELEGRAM_BOT_TOKEN` is not set, the server starts normally but Telegram replies are skipped.

### Register the webhook with Telegram

Run this once (replace values with your token and public URL):
```bash
curl -X POST "https://api.telegram.org/bot<YOUR_TOKEN>/setWebhook" \
     -H "Content-Type: application/json" \
     -d '{"url": "https://yourdomain.com/telegram/webhook"}'
```

Expected response: `{"ok":true,"result":true,"description":"Webhook was set"}`

### Local development with ngrok
```bash
ngrok http 3000
# Copy the https://... URL, then run the setWebhook curl above with that URL
```

### Update payload handled
The endpoint silently accepts and returns 200 for all Telegram update types. Only updates with a `message` field trigger Convex logging and the `"Saved."` reply. Other types (edited messages, callback queries, etc.) are acknowledged and ignored.

## Reliability

### Webhook Retry Handling

Both Twilio (WhatsApp) and Telegram retry webhook deliveries when the server does not respond in time or returns a non-2xx status.

The app includes a best-effort in-memory idempotency guard (`src/idempotency.js`) to handle these retries:

- **WhatsApp (`/sms`)**: The computed reply is cached by `MessageSid` for 5 minutes. Retries within that window return the cached reply immediately, skipping the subscription API lookup and OpenAI call.
- **Telegram (`/telegram/webhook`)**: The bot reply is guarded by `update_id` for 5 minutes. Retries within that window suppress the duplicate `sendMessage` call.

This guard is process-local and non-persistent — it resets on server restart. It is a best-effort safeguard, not a guarantee. For stronger deduplication, a persistent store (e.g. Convex) would be required.

## Development Notes

### Security Considerations

- All sensitive data is stored in environment variables — never hardcode secrets in source files
- `.env` is gitignored and must never be committed; `.env.example` is the safe template
- Session state is in-memory only; do not store secrets in session data

#### Rotate a key if it has been exposed

If any secret (OpenAI key, Telegram token, Twilio credentials, Microsoft client secret) has been committed to git, shared in a log, or was visible in a public place:

1. Revoke it immediately at the issuing provider's dashboard
2. Generate a replacement and update your `.env` file
3. Verify `.env` was never tracked: `git log --all --full-history -- .env`
4. If it was tracked, rewrite history with `git filter-repo` or contact GitHub support to purge the cache

#### Enable the pre-commit secret scan

A lightweight scanner (`scripts/scan-secrets.js`) checks staged files for obvious secret patterns before each commit. To enable it:

```bash
# Copy the script as the git hook (run once per clone)
cp scripts/scan-secrets.js .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

Or create `.git/hooks/pre-commit` manually:

```sh
#!/bin/sh
node scripts/scan-secrets.js
```

To run the scan manually against currently staged files:

```bash
node scripts/scan-secrets.js
```

The scanner detects: OpenAI API keys, Telegram bot tokens, Twilio Account SIDs, Twilio auth tokens, and Microsoft client secret assignments. It reads staged content via `git show`, so it catches secrets in the index even if the working-tree file has been cleaned up.

## Data Retention

A daily cleanup job (`convex/cleanup.js → archiveOldData`) runs at **02:00 UTC** and soft-archives old reminder data. Rows are never deleted — they receive an `archivedAt` timestamp so all data remains recoverable via the Convex dashboard.

### What gets archived

- **Reminders** with status `sent`, `failed`, or `cancelled` whose `runAt` is older than **30 days**.
- **Deliveries** belonging to each archived reminder are archived in the same transaction.
- Active (`queued`) reminders are never touched regardless of age.
- Microsoft Calendar sync job rows (`reminder_sync_jobs`) are not included in this job.

### Batch size and schedule

Each daily run archives at most **200 reminders** (≤ 67 per terminal status). If the backlog exceeds this, subsequent daily runs drain it incrementally.

To adjust the retention window, edit `RETENTION_MS` at the top of `convex/cleanup.js`:

```js
const RETENTION_MS = 30 * 24 * 60 * 60 * 1000;  // 30 days (default)
const RETENTION_MS = 90 * 24 * 60 * 60 * 1000;  // 90 days
```

To change the run time, update the `crons.daily(...)` entry in `convex/crons.js`.

### Recovering archived rows

Archived rows remain in Convex. Query them via the dashboard or a custom query:

```js
ctx.db.query("reminders")
  .withIndex("by_identity", q => q.eq("identityId", id))
  .filter(q => q.neq(q.field("archivedAt"), undefined))
  .collect();
```

## User Settings

Each identity (a `(channel, address)` pair in the `identities` table) can store optional preferences that the system applies automatically when the user does not supply an explicit value.

### Available Settings

- **`defaultTimezone`** — IANA timezone string (e.g. `"Europe/London"`, `"America/New_York"`). When a `/remind` message omits a timezone, this value is used both as the default in the OpenAI extraction prompt and as the JavaScript fallback. If the field is absent, `Australia/Adelaide` is used.
- **`defaultChannel`** — Preferred delivery channel: `"telegram"` or `"whatsapp"`. Applied as `channelPreference` on new reminders when the caller does not override it. If absent, defaults to `"telegram"`.
- **`defaultCalendarProvider`** — Which calendar backend to sync new reminders to:
  - `"microsoft"` — create a Microsoft Outlook Calendar event via Graph API (default if the field is absent).
  - `"none"` — skip calendar sync entirely; no `reminder_sync_jobs` row is created.
  - `"google"` — reserved for a future Google Calendar integration; treated as `"none"` until implemented.

### Mutating Settings

Use the `identities.setIdentitySettings` Convex mutation (e.g. from a future dashboard or admin script). Only the fields you pass are updated; omitted fields are left unchanged:

```js
await convex.mutation(anyApi.identities.setIdentitySettings, {
  identityId: '<id>',
  defaultTimezone:         'Europe/London',
  defaultChannel:          'telegram',
  defaultCalendarProvider: 'none',
});
```

### Backwards Compatibility

All three fields are optional in the schema. Existing identity rows without any settings are unaffected — coded defaults apply exactly as before.

## Rate Limiting

Webhook endpoints are protected by an in-memory rate limiter (`src/rateLimit.js`) with no external dependencies. State is process-local and resets on server restart.

- **POST /sms** (WhatsApp) — 20 requests per minute per sender number (`req.body.From`); falls back to `req.ip` when `From` is absent. Excess requests receive **429** and Twilio will retry with backoff.
- **POST /telegram/webhook** — 30 requests per minute per chat ID. Excess updates are **silently dropped** after the mandatory immediate `200 OK` (Telegram does not retry updates it has delivered).

### Reverse proxy — `TRUST_PROXY`

When running behind a reverse proxy (nginx, Heroku, Railway, etc.) `req.ip` will be the proxy's IP unless you configure Express to trust the `X-Forwarded-For` header.

Set `TRUST_PROXY` in `.env` to the number of proxy hops between the internet and your server:

```env
TRUST_PROXY=1   # single reverse proxy (most common setup)
```

Leave it unset (or empty) when running the server directly without a proxy.

> **Security note**: do not set `TRUST_PROXY` higher than the actual number of proxy hops in your infrastructure. Clients can spoof `X-Forwarded-For`, so a misconfigured value would let them bypass IP-based rate limiting.

## Admin Diagnostics

### `GET /admin/health`

A protected diagnostics endpoint that returns live counts and recent failure details from Convex.

**Authentication**: send the `x-admin-token` header with the value of `ADMIN_TOKEN` from your `.env`.

**Env var**

- `ADMIN_TOKEN` — a strong random secret (e.g. `openssl rand -hex 32`). If unset the endpoint returns 503.

**Example**

```bash
curl -H "x-admin-token: $ADMIN_TOKEN" https://yourdomain.com/admin/health
```

**Response shape**

- `serverTime` — ISO 8601 timestamp of the server at request time
- `version` — value of `version` in `package.json`
- `convex` — `"connected"` | `"not configured"` | `"error"`
- `deliveryCounts` — counts of delivery rows: `{ queued, sent, failed, cancelled }`
- `syncJobCounts` — counts of sync job rows: `{ queued, done, failed }`
- `recentDeliveryFailures` — up to 20 most recently failed deliveries: `{ id, channel, attempts, failureReason, lastAttemptAt, scheduledFor }`
- `recentSyncFailures` — up to 20 most recently failed sync jobs: `{ id, provider, action, attempts, failureReason, lastAttemptAt }`

**Status codes**

- `401` — missing or incorrect `x-admin-token`
- `503` — `ADMIN_TOKEN` or `CONVEX_URL` not configured
- `502` — Convex query succeeded in connecting but threw an error
- `200` — success
